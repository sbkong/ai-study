**벤치마크 기준값 ①** — 1주차 1일 측정 (4096×4096 matmul, `torch.cuda.synchronize()` 적용)

|---|---|
| GPU | 0.0698s |
| CPU | 0.1424s |

> 초회 실행이라 CUDA 컨텍스트 초기화가 포함된 수치다. GPU/CPU 격차가 2배로 작게 나온 이유이며, 실제 격차는 이보다 크다. 워밍업 후 재측정은 5주차 4일(학습 안정화)에서 다룬다.

**벤치마크 기준값 ②** — 1주차 2일 측정 (64 MiB = 4096×4096 float32, 전후 `synchronize()`)

| 항목 | 시간 |
|---|---|
| CPU→GPU 전송 | 0.0480s |
| GPU→CPU 전송 | 0.0420s |
| GPU matmul (같은 셀 첫 실행) | 0.1346s |
| 512×512 텐서 64개로 나눠 전송 | 0.0440s |
| 4096×4096 텐서 1개로 전송 | 0.0400s |

> matmul이 전송보다 3배 느리게 찍혔는데, 이는 해당 셀에서 cuBLAS 초기화가 처음 일어났기 때문이다. 기준값 ①의 0.0698s와도 다르다. 워밍업 후 재측정은 5주차 4일.
>
> 분할 전송 페널티는 10%(0.0440 vs 0.0400)로 작게 나왔다. 512×512 float32 = 1 MiB라 호출당 고정 비용이 상대적으로 작았기 때문이다. 조각을 더 작게(예: 64×64) 쪼개면 격차가 커진다. 2주차 4일 DataLoader에서 `pin_memory`와 함께 다시 본다.

  - **`get_arch_list()`에 `sm_89`가 없는데 정상 동작함.** 목록은 `['sm_75', 'sm_80', 'sm_86', 'sm_90', 'sm_100', 'sm_120']`. CUDA 바이너리는 같은 major 아키텍처 안에서는 하위 minor로 컴파일된 코드가 상위 minor 장치에서 실행된다(sm_86 → sm_89). 즉 "내 sm 번호가 목록에 정확히 있어야 한다"가 아니라 "같은 8.x 계열 중 내 minor 이하 번호가 있으면 된다"가 정확한 규칙이다. 퀴즈 3번 해설을 이 케이스로 보정해 둘 것
  - 최신 torch(2.14.0 / cu13.2)라 Blackwell(sm_120)까지 포함된 휠. 버전 문제로 막힐 여지는 당분간 없음

  1. `xt.view(12)` 실패 · `xt.reshape(12)` 성공 확인 — ✅
  2. `(5,) + (5,1)` → `(5,5)` 에러 없이 발생 확인 — ✅

  4. `memory_allocated` 증가분 = 손계산값 — ⚠️ 0.00 MiB vs 18.38 MiB로 불일치. 상단 미해결 항목 참조
- 커밋: `week01/d2_tensor.ipynb`
- 진행: Step 1~6 전부 완주. 남긴 분량 없음
- 막힌 점: 함수 인자로 들어가는 숫자의 의미 혼동 (아래 메모)
- 퀴즈: 4/5 — 2번 오답
- 1일차 미해결 항목: VRAM·드라이버 모두 기록 완료. 해소됨
- 메모:
  - **퀴즈 2번 오답 — `reshape`의 복사 여부.** `a.t()`는 연속이 아니라 `.reshape(6)`이 복사를 만든다. 따라서 그 결과를 수정해도 원본 `a`는 안 바뀐다. 반면 연속 텐서의 `.view()`는 메모리를 공유하므로 원본이 바뀐다. 정답은 `7.0 0.0`. → **`reshape`은 원본과 연결됐는지가 상황에 따라 달라진다**는 점을 재확인. 판별은 `.data_ptr()` 비교
  - **인자 숫자의 두 종류를 채팅에서 별도 보강.** 헷갈리기 쉬운 지점이라 3일차 이후에도 반복될 가능성 있음
    - 종류① 숫자 = 축의 **길이** → `zeros` `randn` `reshape` `view` `expand`. `view(12)`의 12는 "길이 12"
    - 종류② 숫자 = 축의 **번호** → `argmax(dim=)` `mean(dim=)` `sum(dim=)` `unsqueeze` `squeeze` `flatten(start_dim=)` `permute`. 0부터 왼쪽부터, 음수는 뒤에서부터
    - 구분 단서: 인자 이름에 `dim`이 있으면 종류②. `unsqueeze`/`squeeze`도 실제 시그니처가 `(dim)`이라 종류②
    - `-1`의 뜻이 종류별로 다르다 — 종류①에서는 "남은 길이 자동 계산", 종류②에서는 "마지막 축"
  - **Step 5-3이 0.00 MiB로 찍힌 원인 추정.** 셀을 두 번 이상 실행하면 `base`를 잴 때 이전 `batch`가 아직 살아 있어 base에 18.38 MiB가 이미 포함된다. 그 상태에서 새 텐서를 만들고 `batch`에 재대입하면 이전 텐서가 해제되어 allocated가 base로 돌아오고, 증가분이 0이 된다. → **노트북에서 메모리를 측정할 때는 커널 재시작 직후 1회만 실행한다.** 이 패턴은 앞으로 OOM 진단에서도 그대로 나온다
  - Step 6 4번(`(2,3,4)` → `(4,3,2)`) 관련: `t.view(4,3,2)`는 **에러 없이 통과하지만 전치가 아니다.** 메모리 순서를 그대로 두고 끊는 위치만 바꾸므로 값이 뒤섞인다. `permute`가 필수. 노트북 주석으로 남김
  - 분할 전송 페널티가 10%밖에 안 나온 이유는 조각 하나가 1 MiB로 충분히 컸기 때문. 개념은 확인됐으나 격차가 작아 인상적이지 않았음. 2주차 4일에서 `pin_memory` 비교와 함께 다시 볼 지점
